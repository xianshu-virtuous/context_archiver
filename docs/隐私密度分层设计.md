## 0. 一句话

私聊归档时**一次总结产出两档**：完整版只留在私聊，外流版（印象级）才能在群聊被想起。
**降低泄露密度，而不是阻断通道**——因为通道一断，"她是一个连续的人"这个体验就没了。

## 1. 为什么不做"完全不泄露"

只要跨流共享记忆，绝对不泄露在信息论上就不成立：任何被注入进群聊上下文的内容，都有被复述出来的路径。

所以本设计的目标是**控制密度**：

- 让跨流召回到的文字**本身就是脱敏的**（印象级），即使被复述，也只复述出"她最近经历过什么"，复述不出内容；
- 由**配置与规则**决定放行方向，**不交给模型即兴判断**（这是它和 `cross_stream_relay` 的 relay 机制的根本区别：relay 是概率性的，这里是确定性的）。

**验收口径**：把外流版单独拎出来给人看，读不出任何具体人名、事件、话术、地点与数字，但能看出"这段关系发生了什么变化"。

## 2. 两档内容

| 档 | 字段 | 可见范围 | 用途 |
| --- | --- | --- | --- |
| 完整版 | `content`（沿用现有字段） | 仅来源流 | 私聊里她记得清清楚楚 |
| 外流版 | `gist`（**新增**） | 允许跨流的场景 | 群聊里她"知道有这回事，但说不出细节" |

### 2.1 外流版的生成规则（主人已确认：**关系保留**）

**必须保留**
- 与对方关系的变化与温度（"更亲近了"／"有过一次不愉快"／"约定了一件事"）
- 情绪基调、大致的主题方向、时间锚点

**必须抹除**
- 具体人名、昵称、身份、账号 → 一律用「对方」「那个人」之类的中性指代
- 具体说过的话、具体经过、具体数字、地点
- 身体、亲密、健康、财务等细节
- 任何能让第三方反推出对象或事件的信息

**写法要求**
- 长度 ≤ 完整正文的 `gist_max_ratio`（默认 0.4），通常一到两句
- 陈述语气，不写台词
- 宁可更抽象，也不要为了信息量留下可识别的细节

## 3. 存储方案：为什么不写两条记忆

booku 侧只认 `title` / `content` / 三个标签数组，**没有自定义字段**。备选：

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| A 双条 | 完整版 + 外流版各写一条 booku 记忆 | ✗ 私聊记忆条数翻倍，召回还要去重 |
| B 塞字段 | 把 gist 拼进 content | ✗ 污染正文，召回端还得切分 |
| **C 本地承载（选它）** | 完整版写 booku；**gist 与来源标记记在插件自己的 `memory_index` 里** | ✓ 不翻倍、可控、召回端统一 |

**方案 C 的关键**：`memory_index` 本来就是插件自己的、本来就按 `memory_id` 登记每条记忆（`state.append_memory_index()`，注释里写着"存算一体的「存」半"）。把它升级成**可见性/来源的权威索引**：

```
entry = {
  id, title, snippet, triggers, risk, person_id, stream_id, created_at,   # 现有
  source_stream_type: "private" | "group",     # 新增
  source_stream_id:   "…",                      # 新增
  visibility:         "same_stream" | "portable",  # 新增
  gist:               "…"                        # 新增（私聊才有）
}
```

这样**任何一条召回路线的候选**，都能拿 `memory_id` 查这张表拿到来源与 gist——**不依赖 booku 是否返回 tags**，一次纯本地查表，零网络零模型。

## 4. 召回侧：两道闸门串联

### 4.1 第一道：可见性 + 方向（确定性过滤）

新增 `recall.filter_by_scope(candidates, current_stream, config)`，接在 `recall_for_prompt._run()` **聚合之后、`build_block()` 之前**（聚合点是唯一的，五条路线 person/recent/keyword/triggers/embedding 都在那儿汇合）。

判定矩阵（`found` 表示来源流类型，`cur` 表示当前流类型）：

| 来源 | 当前流 | 配置项 | 默认 | 结果 |
| --- | --- | --- | --- | --- |
| private | private（同流） | — | — | 放行**完整版** |
| private | private（异流） | — | 恒关 | 丢弃 |
| private | group | `private_to_group` | **false** | 默认丢弃 |
| group | private | `group_to_private` | true | 放行（群聊记忆无 gist，原样） |
| group | group（异群） | `group_to_group` | **false** | 默认丢弃 |
| group | group（同群） | — | — | 放行 |
| 未知（老数据） | 任意 | `unknown_source` | **allow** | 默认放行（升级前写下的旧记忆照旧参与跨流召回） |

### 4.2 第二道：正文替换

放行时**不是原样放行**：若命中的是私聊记忆而要进群聊，**用 `gist` 替换 `content`** 再入块。

- `gist` 缺失时的策略 → `gist_missing = "drop" | "raw"`，默认 `"drop"`（宁可少一条，不可漏一段）
- 同一事件若同时召回完整版与 gist，按 `memory_id` 去重，**优先同流版本**

## 5. 配置（新增一个顶层节，风格对齐 `deep_neo_sisp` 的 `[scope]`）

```toml
# 隐私密度分层。让她记得住，但让跨流的那部分"说不出细节"。
[privacy]
# 总开关。关闭 = 完全回到 1.1.x 行为。
# 值类型：bool, 默认值：true   ← 默认开：升级即生效
enabled = true

# 对哪些流做分层。群聊归档通常不敏感，所以默认只做私聊。
# 值类型：list, 默认值：["private"]
apply_to = ["private"]

# 外流版（gist）长度上限，相对完整正文的比例。
# 值类型：float, 默认值：0.4
gist_max_ratio = 0.4

# 外流版是否保留"与对方关系的变化"。关掉更安全，但会削弱人格连续性。
# 值类型：bool, 默认值：true
keep_relationship = true

# gist 缺失时：drop = 直接不注入；raw = 退回完整正文（不建议）。
# 值类型：str, 默认值："drop"
gist_missing = "drop"

# 跨流召回闸门。private_to_group 默认关——这就是"私聊不外流"的那道闸。
[privacy.cross]
private_to_group = false
group_to_private = true
group_to_group = false
# 老数据没有来源标记时的策略：allow = 兼容旧行为（照旧放行）；deny = 最保守（丢弃）。
# 值类型：str, 默认值："allow"
unknown_source = "allow"
```

**默认值取舍（已定：默认开）**：`enabled = true`，配合 `unknown_source = "allow"`，实际效果是一条**分界线**：

- **升级前写下的旧记忆**（没有来源标记）→ `allow` 放行，照旧参与跨流召回，不会因为升级而"突然想不起来"；
- **升级后新写的私聊记忆** → 立刻受方向矩阵约束，`private → group` 默认关掉，进不了群聊。

一句话：**新数据受保护，老数据不失效**。代价是升级行为即刻变化，必须在 CHANGELOG 与 README 里写明"升级即生效、关 `enabled` 可回退"。

## 6. 提示词改动（`archiver._SUMMARY_SYSTEM` / `_SUMMARY_USER`）

按流类型分支：**当前流是私聊且 `[privacy].enabled` 时**，在 user prompt 末尾追加一段（草稿）：

```
【隐私分层要求】本流是私聊，归档必须产出两档内容。

`content` = 完整正文（照原有要求写，细节照留）。
`gist`    = 外流版，它可能在别的场合被想起，所以必须做到：
            读得出一段关系的走向，读不出任何具体内容。

gist 必须保留：
- 与对方关系的变化与温度（更亲近了 / 有过一次不愉快 / 约定了一件事）
- 情绪基调、大致主题方向、时间

gist 必须抹除：
- 具体人名、昵称、身份、账号（一律用「对方」指代）
- 具体说过的话、具体经过、具体数字与地点
- 身体、亲密、健康、财务等细节
- 任何能让第三方反推出对象或事件的信息

写法：不超过完整正文的 40%，通常一到两句，陈述语气，不写台词。
宁可更抽象，也不要为了信息量留下可识别的细节。
```

对应地，输出 JSON 的 `memories[]` 每项多一个 `gist` 字段：
`{title, content, gist, memory_type, core_tags, diffusion_tags, opposing_tags, triggers, risk}`

## 8. 测试清单（沿用 `tests/check_logic.py` 风格，纯逻辑、不连模型）

1. **提示词分流**：私聊 + `enabled` → 含隐私段；群聊 → 不含
2. **gist 解析**：正常 / 缺失 / 超长（按 `gist_max_ratio` 截断） / 空串
3. **标签与索引写入**：可见性、来源类型、来源流 id 正确落库
4. **过滤矩阵**：§4.1 表里 7 行逐行断言
5. **gist 替换**：私聊记忆进群聊 → 注入的是 gist，不是 content
6. **gist 缺失兜底**：`drop` 与 `raw` 两种行为
7. **去重**：同一 `memory_id` 的完整版与 gist 同时召回 → 只留一条
8. **老数据兼容**：索引里没有新字段 → 按 `unknown_source` 处理（默认 `allow`，即照旧参与召回）
9. **默认开**：配置缺省时 `enabled` 为 `true`，新写私聊记忆立即受 `private_to_group = false` 约束

## 9. 口味已定（主人 2026-10-08 拍板）

| # | 问题 | 决定 |
| --- | --- | --- |
| 1 | `[privacy].enabled` 默认值 | **`true`** —— 默认开，升级即生效 |
| 2 | `unknown_source` 默认值 | **`"allow"`** —— 旧记忆照旧参与跨流召回，不因升级而失效 |
| 3 | 是否在 README 写明 relay 可退役 | **写明** —— 跨流意识改走"确定性通路 + 密度分层" |

因"默认开"而生的两条配套要求：

- **CHANGELOG 置顶写明**：升级后**新写的**私聊记忆默认不再进群聊；想回到旧行为就设 `enabled = false`（旧记忆因 `allow` 不受影响）；
- **README 给一张对照表**：同一件事，在私聊里她记得什么、在群里她最多能说到什么程度——让"密度分层"一眼可懂。

## 10. 风险与回滚

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 抽象质量依赖模型 | 过度抽象 → gist 无信息量；抽象不足 → 仍可识别 | 提示词里给"读得出关系、读不出内容"的验收口径；先小样本人工抽查 |
| 本地索引体积 | 每条多存一段 gist | 索引本就有 `_MEMORY_INDEX_KEEP` 上界；gist 限长 0.4 |
| 召回质量下降 | 跨流召回的候选变少 | `group_to_private` 默认放行，保证"她在私聊里仍知道外面的事" |
| **默认开带来的行为突变** | 升级后新写的私聊记忆立刻不再进群聊，主人若没预期会觉得"她怎么不记得了" | CHANGELOG + README 置顶说明；`enabled = false` 一键回到旧行为 |
| 需要回滚 | —— | 关 `[privacy].enabled` 即回到 1.1.x 行为；无需迁移数据 |

## 11. 验收（实现后怎么算过）

1. 在实例上跑一轮真实私聊归档 → 查 booku 里的标签、本地索引里的 gist 是否落位；
2. 切到群聊聊相关话题 → 确认注入块里出现的是 gist 文本而非完整正文；
3. 把注入块原文拿给第三人看 → 读不出具体人名/事件/话术；
4. 回归：关掉 `[privacy].enabled` → 行为与 1.1.3 一致；
5. 旧记忆：升级前写下的记忆仍能在跨流被召回（`unknown_source = "allow"` 生效）；
6. 默认开：全新配置（无 `[privacy]` 段）启动后，`enabled` 取到 `true`。

## 附：与现存机制的关系

| 机制 | 管什么 | 与本功能的分工 |
| --- | --- | --- |
| `cross_stream_relay` 的 `[privacy] private_bridge_mode` | 摘要层面的方向 | 确定性，但只做"摘要"这一种粒度，且摘要本身没做脱敏 |
| `cross_stream_relay` 的 `[relay] enabled` | LLM 主动交接 | **概率性**，隐私上不可靠；本功能上线后可以不依赖它 |
| `deep_neo_sisp` 的 `[scope]` | 插件在哪些群/人身上生效 | 那是"生效范围"，与"记忆往哪流"正交，可各自独立配置 |
| 本功能 | 记忆的**密度**与**方向** | 两层串联：分层决定"流过去的是什么"，闸门决定"能不能流" |
