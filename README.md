# 上下文归档器（context_archiver）

**让 Bot 记得住，而且不用调工具就能想起来。**

这个插件做三件事，顺序就是重要性：

1. **主动把对话沉淀成记忆**——按「Bot 有没有参与」判定，Bot 停口就把这段经历写进
   `booku_memory`。不等群彻底安静，所以话痨群里的 Bot 也记得住事。
2. **存算一体：写的时候就算好，读的时候零成本**——写记忆时顺手让模型吐出「这条记忆在
   什么场景下会被想起来」（触发词），之后每轮拿当前对话跟这张本地表做**字符串匹配**，
   把该记得的自动捞回来塞进上下文。**查询侧零 LLM、零网络、零 tool 调用。**
3. **（可选）话题结束时清空该流上下文**——顺带省钱，是上面的副产品，不是卖点。

---

## 它解决什么问题

Bot 的记忆有两个老毛病：

**一、上下文一长就糊涂、一清就失忆。** 每轮背着几万 token 的历史，其中绝大部分对
「这一轮该说什么」早就没有新信息了；而真清掉，这段经历就真的没了——除非先写进记忆。

**二、想记起来得靠自己调工具，而它经常想不起来调。** 记忆工具是 agent 的一次额外循环：
一次 0.0350 元，而且**模型是否调用全凭自觉**——该想起水壶坏了的时候，它常常想不起来。

所以本插件把「写」和「读」都变成系统行为：

- **写**：不需要 Bot 下决心，判定到了就写。
- **读**：不需要 Bot 调工具，prompt 构建时自动注入。

实测一个真实实例（13 天、3810 次 LLM 请求）的上下文体积，说明「背着历史说话」有多重：

| 项 | 实测值 |
| --- | --- |
| 输入 token 占总消耗 | **98.4%**（输出只占 1.6%） |
| `default_chatter` 单轮平均输入 | **59,107** token（峰值 101,542） |
| 其中 system prompt + 工具/动作声明 | 约 41,000 token |
| 每轮**全价**（未命中缓存）的部分 | 约 8,561 token |
| 单轮平均成本 | 约 0.035 元 |

最后一列也是「为什么必须少一次 tool 调用」：那 0.035 元不是被对话本身吃掉的，
是被**每一步额外的模型循环**吃掉的。

## 它怎么工作

```
收到消息 ──► 记活跃（每流一份）
    │
    └─ Bot 调 stop_conversation ──► 记结束信号

每 tick 巡检一次（默认 15s）：
    │
    ├─ 有结束信号？ ──等待落库──► 归档
    ├─ Bot 停口超过 idle_seconds？ ─────► 归档（写记忆）
    ├─ 累积够 turn_threshold 条？ ─────► 归档（只写记忆，绝不清空）
    │
    └─ 归档链路（顺序不能换）：
         ① 取水位线之后的消息（不重复总结）
         ② 上次摘要 + 本次对话 → 新摘要 + 若干记忆条目
            （每条带 触发词 triggers 与 风险标记 risk —— 这就是「存算一体」的「算」）
         ③ 写进 booku_memory，并把 id/title/片段/触发词 登记进本地记忆索引
         ④ ③ 成功后才清空上下文（写持久水位线）
         ⑤ 无论成败都写一条审计

每轮 prompt 构建时（默认对所有 user prompt 生效）：
    └─ 拿最近的对话文本 → 匹配本地记忆索引 + 查 booku 元数据
         → 命中就注入 user prompt 的 extra（默认 ≤900 字符）
         → Bot 一次 tool 都没调
```

### 判定优先级

| 优先级 | 判据 | 说明 |
| --- | --- | --- |
| 1 | **结束信号** | Bot 自己调了 `stop_conversation`（「结束这一轮，让外部决定何时再次启动」）。等 `settle_seconds` 让消息落库后归档。 |
| 2 | **Bot 停口** | 没有结束信号时，**Bot 上次发言**之后静默超过 `idle_seconds` 就归档。 |
| 3 | **条数兜底** | 该流累积够 `turn_threshold` 条消息就归档一次，不等静默。 |

> **第 2 条的基准是「Bot 有没有参与」，不是「流有没有消息」。**
> 群里别人一直说话、Bot 也一直在接话时，按「流安静」判就永远不会触发——
> 这个坑踩过：原先的实现是「群聊完全没动静才写」，结果话痨群一条记忆都写不出来。
> 现在看的是 `last_engagement_at`（Bot 自己的发言时间），群聊再热也不影响。
>
> 另外，`turn_trigger` 这条**只写记忆、绝不清空上下文**——话题可能还在继续。

> **`pass_and_wait` 不算结束**。它的语义是「挂起，准备恢复」，把它当结束会频繁切断对话。

### 与 time_sense 的关系

**软依赖，manifest 里不写它。** 框架对 `dependencies.plugins` 里的缺失插件是**硬剔除**
（`dependencies_required: false` 也救不回来），所以「有更好、没有也能跑」的关系
只能靠运行时探测：取得到 `time_sense:service:time_sense` 就用它交叉验证，
取不到就退回纯「Bot 停口」判定，功能不受影响。

## 存算一体：为什么关联要写在「写」的时候

用户真正想要的记忆是这样的：

```
记忆条目：水壶昨天就坏了，有点漏电
用户输入：好渴啊，有点想喝水
期望行为：Bot 提醒「别用那个水壶接电」
```

「渴」和「水壶漏电」之间没有字面重叠、向量上也未必是近邻——**这条关联是个常识边**，
只有理解了内容的人才能画出来。所以本插件把它画在**写入时**（那时总结模型手里正好有
这条记忆的全文），读取时就只是一次查表：

| 路线 | 能命中「渴 → 水壶漏电」？ | 查询成本 |
| --- | --- | --- |
| 向量检索 | 靠语义近邻，未必；且「渴」没有同义关联 | 每轮一次 embedding 网络调用 |
| 关键词 grep | 不能，字面上没有公共词 | 本地，但词要抠得准 |
| **触发词（本插件）** | **能**——触发词里就写着 `喝水 / 渴 / 水壶 / 漏电` | **纯本地字符串匹配，零 LLM** |

写入时多做一点（每条记忆多输出 3~8 个触发词，约几十 token 的输出），
读取时白拿一次关联。写记忆是低频动作（默认 ≥30 秒静默才一次），读是每轮都读——
**把成本放在低频侧，是高杠杆。**

实现上就是一张本地倒排表：

```
data/json_storage/context_archiver/memory_index
  [{ id, title, snippet, triggers: ["水壶","喝水","渴","烧水","漏电"],
     risk: "high", person, stream, at }, ...]   （最多保留 800 条）
```

每轮拿 `unreads + history 尾部` 做一次包含匹配，打分排序：

- 多字命中的触发词每个 +1.5，单字命中每个 +0.5，底分 3.0
- **佐证门槛**：只有单字命中且不足两个 → 丢弃（光一个「水」字不值得惊动一条记忆）
- `risk == "high"`（安全/健康/承诺/金钱）+1.5
- 人物一致（这条记忆本来就属于当前对话者）+1.0
- 时间衰减 `0.5 ** (小时数 / 72)`，新鲜的事更容易被想起来

命中的条目在注入时会带 `⚠` 前缀，明确告诉模型「这条该主动提」。
整个过程是微秒级的本地操作，所以它就直接跑在 prompt 构建的同步路径上。

## 召回：三条路线 + 一个目标

目标只有一个：**Bot 不需要调用任何记忆工具**，插件在 prompt 构建时把该记得的塞进
user prompt 的 `extra`（默认 ≤900 字符，约 600 token）。

| 路线 | 用什么 | 特点 |
| --- | --- | --- |
| `trigger` | 本地记忆索引的触发词包含匹配 | **存算一体的读半**，零 LLM、零网络，能命中常识关联 |
| `person` | `list_memory_entries(person_id=…)` | 精确：关于当前对话者的事 |
| `recent` | 同接口按 `last_activated_at` 倒序 | 稳：最近被想起过的事，不需要关键词 |
| `keyword` | `grep_memories` 字符级匹配 | 默认关：中文没分词，抠词容易出噪音 |
| `embedding` | `retrieve_memories`（向量） | 语义相近，代价是每轮一次 embedding 调用 |

`recall.mode` 决定跑哪几条：`trigger`（只跑触发词）/ `structured`（默认：触发词 + 人物 +
近因）/ `embedding` / `both`。

**闭环**：召回命中后会调 `update_activated` 抬高激活计数。booku 的隐现层会在 7 天内淘汰
激活不足 2 次的记忆，而被召回过的东西本来就该留下——**读得越多，记忆越稳**。
（写入时也会先抬 1 次：不这么做，新记忆的 `activation_count = 0`，在
`last_activated_at.desc()` 排序里永远排不上队、永远召不回来、7 天后被丢掉——是个死锁。）

## 快速开始（建议按这个顺序）

**第一步：先只观察。**

默认就是 observer 模式——它只记录、只打日志，不总结、不写记忆、不清空。
先放几天，看日志里「**将归档**」出现的时机对不对：

```
[context_archiver][observer] stream=4c96dd6a **将归档**：Bot 已 42s 没参与（阈值 30s）
```

**第二步：看看它打算总结什么。**

- `/归档 流` 看当前流的判定原因与待归档条数
- `/归档 演练` 对当前流跑一次「只总结不落盘」的预演，直接看摘要和记忆条目质量

**第三步：确认没问题再开执行。**

```
/归档 active          # 只改运行时，重启后回到配置文件的值
```

然后在 `config.toml` 里把 `plugin.mode` 改成 `active` 固化下来。
开了之后 `/归档 审计` 能看到每条记忆的 id，`/归档 召回` 能看到每轮注入了什么。

**第四步（可选、谨慎）：开清空。**

```toml
[archive]
clear_context_enabled = true
```

**清空是不可逆的**：框架写的是 `ChatStreams.context_cleared_at` 水位线，
消息记录还在数据库里，但默认不再进入对话上下文，重启后依然生效。
只有「总结 → 记忆写入成功」之后才会真正调用它；写失败就跳过清空。

## 命令

仅主人可用（会触发真实记忆写入）。

```
/归档                状态总览 + 各流概况
/归档 审计           最近几次归档做了什么（时间区间、条数、摘要、memory_id、是否清空）
/归档 注入           提示词构成归因：每轮的钱花在哪
/归档 召回           最近的召回记录：注入了哪几条、来自哪条路
/归档 流             当前流的详细状态与判定原因
/归档 演练           只总结不落盘（看摘要质量用）
/归档 现在           立刻归档当前流
/归档 模式           查看运行模式
/归档 observer       切到观察模式
/归档 active         切到执行模式
```

## 配置

配置文件：`config/plugins/context_archiver/config.toml`（首次加载自动生成）

### `[plugin]`

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 总开关（关闭后连活跃都不记） |
| `mode` | `observer` | `observer` 只观察；`active` 才真正总结、写记忆 |
| `debug_log` | `false` | 调试日志 |

### `[trigger]`

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `tick_seconds` | `15` | 巡检间隔（必须明显小于 `idle_seconds`） |
| `settle_seconds` | `90` | 收到结束信号后等多久（让消息落库） |
| `idle_seconds` | `30` | **Bot 停口**多久算这一轮过去了（写记忆的主阈值） |
| `min_messages` | `4` | 少于这么多条不折腾（短寒暄不值得一次模型调用） |
| `max_messages` | `400` | 单次最多取多少条消息 |
| `use_time_sense` | `true` | 有 time_sense 就交叉验证 |
| `require_global_quiet` | `false` | 是否要求「别的流也安静」才归档。**默认关**：判定按流独立进行 |
| `turn_trigger_enabled` | `true` | 条数触发（与静默是「或」的关系） |
| `turn_threshold` | `100` | 累积多少条触发一次（只写记忆，不清空） |

> 话痨实例建议：`idle_seconds = 300`、`min_messages = 20`——把「每 5 分钟一次」当节奏，
> 避免每 30 秒就花一次模型调用。

## 关于「省钱」：诚实版

这个插件**不承诺省钱**。写记忆、注入召回都要花 token，实测归因是：

| 成分 | 占单轮成本 |
| --- | --- |
| 命中的输入（缓存价，便宜） | 15% |
| **未命中的输入（全价）** | **74%** |
| 输出 | 11% |

而那部分全价输入（平均 8,561 token/轮）**与历史长度几乎无关**——
输入从 3.2 万涨到 8.2 万 token，命中率反而从 18% 掉到 11%，
`corr(输入体积, 未命中量) = +0.14`。也就是说：**贵的是「每轮都在变的东西」，不是「历史太长」。**

推论有三条，都在本插件的取舍里：

1. **清空上下文省不了大钱**（历史只占模板里约 1.7%，加上压缩调用的消失也就 5~16%）。
   所以 `clear_context_enabled` 默认关，它是「顺便」，不是目的。
2. **省钱的唯一大头是「换更便宜的模型 + 少几次循环」**——这也是为什么本插件坚持
   零 tool 调用，并且把总结指到便宜模型上（`[model]`）。
3. **框架的缓存布局已经是好的**（实测稳定前缀约 96,600 字符，未命中只来自尾部增量），
   所以本插件不去折腾「缓存友好的重排」。

本插件顺手做两件只读的度量，供自己判断：挂在 `ON_PROMPT_BUILD` 上逐轮记
`history / unreads / extra` 的字符数，挂在 `BEFORE_LLM_REQUEST` 上把「工具声明」
和「各角色 payload」分开数。`/归档 注入` 能直接回答「那 8.5k 全价 token 是谁塞的」。
**先量，再削。**

## 三个必须知道的坑

**1. `booku_memory` 会丢新记忆。**
新写的记忆默认进隐现层，7 天内被激活少于 2 次的会被自动丢弃（`emergent_days=7` /
`activation_threshold=2`）。本插件用两次 `update_activated`（写入时 1 次、召回时 1 次）
把它顶过阈值；想要必留，把 `memory.status` 配成 `archived`——代价是默认检索不搜归档层。
这是取舍，不是 bug。

**2. `create_memory` 要求三个标签都非空。**
少一个直接抛错。本插件一定会用配置里的兜底标签补齐，所以别把三组标签都清空。

**3. 触发词的质量决定了关联的质量。**
触发词是总结模型写的：它写 `喝水 / 渴`，那条水壶记忆就能被「想喝水」捞出来；
它忘了写，就捞不出来。所以建议 `/归档 演练` 时看一眼模型给的 triggers 是否靠谱。
另外索引是本地有界表（最多 800 条），不参与 booku 的淘汰规则——删掉它会重新从
后续写入开始积累。

## 跟已有插件的关系（诚实版）

同一个生态里已经有几件事被做过了，这里说清楚边界，不重复造轮子：

| 已有 | 它做了什么 | 本插件的区别 |
| --- | --- | --- |
| `cross_stream_relay` / `send_to` | 增量短期记忆、水位线、跨天归档、跨流摘要 | 它们写**自己的 json**、用于跨流互通；本插件写**booku_memory 的 RAG 库**，并且做**零 tool 的自动召回**与**存算一体触发词**——后者没人做 |
| 框架自带 `context_compression` | 上下文逼近上限（95%）时压缩 | 它是**被动、晚、只在内存里替换**；本插件是**主动、早、持久**，且顺手写记忆 |
| `booku_memory` 的闪回 | 随机抽一条旧记忆注入 | 它是随机唤起；本插件是**相关性驱动**（触发词/人物/近因），且写的时候就算好了关联 |

「增量总结 + 水位线」这套思路与 `cross_stream_relay` 有重叠，**代码是自写的**，
在此向原作者致谢（见下）。如果你的 Bot 已经在用 `cross_stream_relay` 做跨流摘要，
本插件不会跟它抢同一份数据，两者可以并存。

## 边界与已知取舍

- **清不掉的地板**：实测 `default_chatter` 的最小输入是 **27,400** token
  （system prompt + 工具/动作声明）。清空历史最多把这部分之外的都省掉，
  地板本身与本插件无关——想再往下压得从工具暴露面下手。
- **判定永远是启发式的**：`stop_conversation` 的调用率取决于模型行为，
  框架也没把 action 落盘（`action_records` 表是空的），所以先跑几天 observer 再定阈值。
- **触发词匹配是字面的**：它靠写记忆时算好的那张表，抗不住「字面完全无关、
  连总结模型也没预料到」的跨领域联想。要更强得在查询侧加语义，那就要付每轮的 embedding 钱——
  本插件默认不花这笔钱。
- **多 Bot 共用一个 data 目录**时状态会互相覆盖（跟 `time_sense` 一样的约束）：
  一个 Bot 一个 data 目录。

## 数据落盘

```
data/json_storage/context_archiver/streams          # 每流状态与滚动摘要
data/json_storage/context_archiver/audit            # 归档审计（最近 N 条）
data/json_storage/context_archiver/local_memories   # sink=local 或 booku 不可用时的兜底
data/json_storage/context_archiver/memory_index     # 存算一体的「存」：触发词索引（最多 800 条）
```

删掉 `streams` 等于让它忘掉水位线：下次会把能取到的消息重新总结一遍
（不会重复清空，但会重复写记忆）。慎删。
