# 上下文归档器（context_archiver）

**话题结束了，就把这段对话总结进记忆，然后清空这个聊天流的上下文。**

Bot 不用再每轮背着整段历史说话，但它依然记得发生过什么。

---

## 它解决什么问题

Bot 的上下文会一直长。实测一个真实实例（13 天、3810 次 LLM 请求）：

| 项 | 实测值 |
| --- | --- |
| 输入 token 占总消耗 | **98.4%**（输出只占 1.6%） |
| `default_chatter` 单轮平均输入 | **59,107** token（峰值 101,542） |
| 其中每轮**全价**（未命中缓存）的部分 | 约 8,561 token |
| 单轮平均成本 | 约 0.035 元 |

也就是说：**贵的是每轮带着的那一大段历史**，而不是 Bot 说了多少话。
而历史里绝大部分内容，对「这一轮该说什么」早就没有新信息了——
它只是还没被送进记忆、也还没被清掉。

这个插件做的就是收尾动作：**总结 → 记下 → 清空**。

> 顺带说明一个常见误解：清空省下的不只是「命中缓存那部分很便宜的钱」。
> 一次性删掉整段历史之后，那几万 token 根本不用发送，也不用参与任何计算。

---

## 它怎么工作

```
收到消息 ──► 记活跃（每流一份）
    │
    └─ Bot 调 stop_conversation ──► 记结束信号

每 tick 巡检一次：
    │
    ├─ 有结束信号？ ──等待落库──► 归档
    ├─ 没有？静默超阈值？ ─────► 归档
    │
    └─ 归档链路（顺序不能换）：
         ① 取水位线之后的消息（不重复总结）
         ② 上次摘要 + 本次对话 → 新摘要 + 若干记忆条目
         ③ 写进 booku_memory（失败降级本地 json，绝不静默丢）
         ④ ③ 成功后才清空上下文（写持久水位线）
         ⑤ 无论成败都写一条审计
```

### 判定优先级

| 优先级 | 判据 | 说明 |
| --- | --- | --- |
| 1 | **结束信号** | Bot 自己调了 `stop_conversation`（「结束这一轮，让外部决定何时再次启动」）。等 `settle_seconds` 让消息落库后归档。 |
| 2 | **闲置兜底** | 没有结束信号时，该流静默超过 `idle_seconds` 视为话题已停。 |
| 3 | **全局静默校验** | 装了 `time_sense` 时，用它的「距上次说话」确认**别的流也没在聊**（它记的是全局值）。避免「私聊静默、群聊在聊」被误判。 |

> **`pass_and_wait` 不算结束**。它的语义是「挂起，准备恢复」，把它当结束会频繁切断对话。

### 与 time_sense 的关系

**软依赖，manifest 里不写它。** 框架对 `dependencies.plugins` 里的缺失插件是**硬剔除**
（`dependencies_required: false` 也救不回来），所以「有更好、没有也能跑」的关系
只能靠运行时探测：取得到 `time_sense:service:time_sense` 就用它交叉验证，
取不到就退回纯闲置判定，功能不受影响。

装了 `time_sense` 之后你会白拿两件事：判定与它的心跳节奏天然对齐；跨重启的静默时长是准的。

## 快速开始（建议按这个顺序）

**第一步：先只观察。**

默认就是 observer 模式——它只记录、只打日志，不总结、不写记忆、不清空。
先放几天，看日志里「**将归档**」出现的时机对不对：

```
[context_archiver][observer] stream=4c96dd6a **将归档**：收到结束信号 stop_conversation（已过 92s）
```

**第二步：看看它打算总结什么。**

- `/归档 流` 看当前流的判定原因与待归档条数
- `/归档 演练` 对当前流跑一次「只总结不落盘」的预演，直接看摘要质量

**第三步：确认没问题再开执行。**

```
/归档 active          # 只改运行时，重启后回到配置文件的值
```

然后在 `config.toml` 里把 `plugin.mode` 改成 `active` 固化下来。

**第四步（可选、谨慎）：开清空。**

```toml
[archive]
clear_context_enabled = true
```

**清空是不可逆的**：框架写的是 `ChatStreams.context_cleared_at` 水位线，
消息记录还在数据库里，但默认不再进入对话上下文，重启后依然生效。
只有「总结 → 记忆写入成功」之后才会真正调用它；写失败就跳过清空。

## 命令

仅主人可用（会触发真实记忆写入）。

```
/归档                状态总览 + 各流概况
/归档 审计           最近几次归档做了什么（时间区间、条数、摘要、memory_id、是否清空）
/归档 流             当前流的详细状态与判定原因
/归档 演练           只总结不落盘（看摘要质量用）
/归档 现在           立刻归档当前流
/归档 模式           查看运行模式
/归档 observer       切到观察模式
/归档 active         切到执行模式
```

## 配置

配置文件：`config/plugins/context_archiver/config.toml`（首次加载自动生成）

### `[plugin]`

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 总开关（关闭后连活跃都不记） |
| `mode` | `observer` | `observer` 只观察；`active` 才真正总结、写记忆 |
| `debug_log` | `false` | 调试日志 |

### `[trigger]`

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `tick_seconds` | `60` | 巡检间隔 |
| `settle_seconds` | `90` | 收到结束信号后等多久（让消息落库） |
| `idle_seconds` | `1800` | 无结束信号时的静默兜底阈值 |
| `min_messages` | `4` | 少于这么多条不折腾（短寒暄不值得一次模型调用） |
| `max_messages` | `400` | 单次最多取多少条消息 |
| `use_time_sense` | `true` | 有 time_sense 就交叉验证 |
| `require_global_quiet` | `true` | 要求全局也安静才归档 |

### `[archive]`

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `clear_context_enabled` | `false` | **清空开关**，单独一个，不跟 mode 一起开 |
| `inject_summary_after_clear` | `true` | 清空后把滚动摘要注入回去（「清空但不忘事」） |
| `summary_max_chars` | `1200` | 滚动摘要上限 |
| `max_digest_chars` | `24000` | 喂给模型的对话文本上限 |

### `[model]`

默认跟随主回复模型（`task_name = "actor"`）。总结是个轻活，想省钱可以
`model_name = "deepseek-v4-flash"` 直接点名。

### `[memory]`

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `sink` | `booku` | `booku` / `local` / `none` |
| `status` | `active` | `active` 进隐现层（可检索，7 天不激活会被 booku 丢弃）；`archived` 进归档层（不会被丢，但默认检索不搜） |
| `bucket` | `memory` | 只有 `memory` / `knowledge` 有效 |
| `core_tags` 等三组 | 见注释 | **兜底标签**：booku 要求三元组都非空，模型没给就用它 |
| `attach_person` | `true` | 给记忆挂上对话者 |

## 三个必须知道的坑

**1. `booku_memory` 会丢新记忆。**
新写的记忆默认进隐现层，7 天内被激活少于 2 次的会被自动丢弃（`emergent_days=7` /
`activation_threshold=2`）。想要必留，把 `memory.status` 配成 `archived`——
代价是默认检索不搜归档层，得靠闪回或显式 `include_archived` 才读得到。
这是取舍，不是 bug。

**2. `create_memory` 要求三个标签都非空。**
少一个直接抛错。本插件一定会用配置里的兜底标签补齐，所以别把三组标签都清空。

**3. 清空之后，Bot 只能靠记忆和摘要记得。**
所以本插件额外维护一份**每流的滚动摘要**，清空后作为背景注入回去
（注入位置是 user prompt 的 `extra`，跟在历史之后，不影响前缀缓存）。
摘要烂了，这段经历就是真的模糊了——这也是为什么建议先跑 `/归档 演练` 看摘要质量。

## 跟已有插件的关系（诚实版）

同一个生态里已经有几件事被做过了，这里说清楚边界，不重复造轮子：

| 已有 | 它做了什么 | 本插件的区别 |
| --- | --- | --- |
| `cross_stream_relay` / `send_to` | 增量短期记忆、水位线、跨天归档、跨流摘要 | 它们写**自己的 json**、用于跨流互通；本插件写**booku_memory 的 RAG 库**，并且会**清空上下文**——后者没人做 |
| 框架自带 `context_compression` | 上下文逼近上限（95%）时压缩 | 它是**被动、晚、只在内存里替换**；本插件是**主动、早、持久清空**，且顺手写记忆 |
| `booku_memory` 的闪回 | 随机抽一条旧记忆注入 | 它是随机唤起；本插件是「这段对话的来龙去脉」整体沉淀 |

「增量总结 + 水位线」这套思路与 `cross_stream_relay` 有重叠，**代码是自写的**，
在此向原作者致谢（见下）。如果你的 Bot 已经在用 `cross_stream_relay` 做跨流摘要，
本插件不会跟它抢同一份数据，两者可以并存。

---

## 边界与已知取舍

- **清不掉的地板**：实测 `default_chatter` 的最小输入是 **27,400** token
  （system prompt + 工具/动作声明）。清空历史最多把这部分之外的都省掉，
  地板本身与本插件无关——想再往下压得从工具暴露面下手。
- **判定永远是启发式的**：`stop_conversation` 的调用率取决于模型行为，
  框架也没把 action 落盘（`action_records` 表是空的），所以先跑几天 observer 再定阈值。
- **多 Bot 共用一个 data 目录**时状态会互相覆盖（跟 `time_sense` 一样的约束）：
  一个 Bot 一个 data 目录。

## 数据落盘

```
data/json_storage/context_archiver/streams          # 每流状态与滚动摘要
data/json_storage/context_archiver/audit            # 归档审计（最近 N 条）
data/json_storage/context_archiver/local_memories   # sink=local 或 booku 不可用时的兜底
```

删掉 `streams` 等于让它忘掉水位线：下次会把能取到的消息重新总结一遍
（不会重复清空，但会重复写记忆）。慎删。
